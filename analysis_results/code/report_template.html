ROI tracking and accumulated fields

Diaplacement_run moved the ROI by minus the measured displacement, and moved all four edges by the same mean value. The paper's data moves material at x to x + u (Section 2.2), so the ROI must move by +u. Its Figure 14 also shows the ROI stretching from 188×374 to 178×434 px during the bronze test, which a single mean shift cannot do. The fixed cell flips the sign and moves each edge by the displacement measured along that edge.

To check it, I made a 40-frame synthetic tensile test with known motion (16% vertical stretch, Poisson contraction, 16 px sideways drift) and ran the notebook's own ROI cell on it with the longer-trained DisplacementNet.

Accumulated displacement and strain

The paper adds each frame's increment into accumulated fields (Figure 2) and reports strain as εxx, εyy and εxy. The run notebooks saved only increments, and StrainNet_run saved four raw gradients at half size. Without changing any existing output, they now also save disp_acc, strain_xx_yy_xy and strain_acc. The accumulated fields are kept on the starting ROI's grid, where each pixel follows one material point. εxy is the symmetric part of the gradients, so rigid rotation cancels, and the cross terms are corrected for the resize to multiples of 32. StrainNet_run also now uses the same ROI as DisplacementNet for each frame pair; before, it was one frame ahead.

Why StrainNet did not learn

A flat loss can mean a bug, so I checked three things separately.

QuestionResultConclusion
Are the strain labels right?Strain differentiated from optical flow correlates with them at {{CORR_FLOW}} or higher on all four channels.Labels and channel order are consistent
Did the trained network learn?Its predictions correlate with the labels at {{CORR_PRED}} at best, and they vary far less (standard deviation {{PRED_STD}} against {{LABEL_STD}}).Output is nearly constant
Can the pipeline learn at all?On 12 fixed images, loss fell from {{OVER_START}} to {{OVER_END}}, or {{OVER_DROP}}% lower, in 240 steps.The code path works

So the pipeline is sound and the {{STEPS_S}} training steps were too few. Strain needs the difference in displacement between nearby points, which is a harder signal to learn than overall motion. This rules out a broken pipeline, but it does not prove that full training will reach the paper's accuracy. The longer run below tests that.

Where the code differs from the paper

The network is left as committed, because changing it would stop the published pretrained weights from loading. The training schedule, ROI tracking and outputs now follow the paper.

The network has {{PARAMS}} million parameters and needs {{MACS}} billion multiply-accumulate operations per 128×128 pair. Inputs must be multiples of 32 pixels in both directions. {{UNUSED}} parameters in conv1 and fc are never used, but they must stay for the pretrained weights to load.

Still to check with the authors' data

  1. Strain channel order. np.gradient returns the row derivative first, so the channel named dudx is really ∂u/∂row if channel 0 of the labels is the horizontal u. StrainNet_run's new εxx, εyy, εxy assume exactly that. If the authors' .mat files store the fields the other way round, swap εxx and εyy.
  2. StrainNet convergence. After {{L_STEPS_S}} steps StrainNet has learned one of its four channels, and its output still depends on the input size. The paper's StrainNet error fell within its first few epochs (Figure 7), and one epoch of its 36,000 pairs is 3,000 steps at batch 12. Whether full training removes the size dependence needs a GPU run.
  3. Dataset statistics. Table 2 gives parameter ranges but not how they were sampled. Uniform sampling, as here, gives deformations 4–10 times larger than the paper's Figure A-1. The authors' dataset would show which sampling they used.
  4. Image format. The loaders now convert images to 8-bit greyscale. That matches two-channel input, but I could not inspect the authors' files.
